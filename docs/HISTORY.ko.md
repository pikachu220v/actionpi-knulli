# 개발 이력과 최종 구성의 이유

[English](HISTORY.md) · [한국어](HISTORY.ko.md)

## 1. 정상 부팅 기준본 보존

처음 목표는 모든 에뮬레이터가 아닌 PPSSPP에서 Vulkan을 사용하는 것이었습니다.
초기 TSPS식 접근은 Mali r32/r42 표기 비교나 PPSSPP 옵션 변경으로 단순화하기 쉬웠지만,
실제로는 커널 모듈, 사용자 공간 Mali 라이브러리, Vulkan ICD 등록, SDL과 실행 환경이
모두 맞아야 했습니다.

여러 시험 이미지가 메뉴에 도달하기 전에 실패했습니다. 이미 변경한 이미지에서 Wi-Fi
파일 하나를 넣거나 빼는 것으로 깨끗한 기준본이 되지는 않았습니다. 정상 부팅이 확인된
v87부터 다시 시작하고, 작동하는 지점을 보존하는 방식으로 진행했습니다. 순정 펌웨어에서
Wi-Fi 하드웨어가 정상임을 확인했습니다. 최종 구성은 순정에 들어 있던 모든 Wi-Fi
모듈을 서로 바꿔 쓸 수 있다고 보지 않고, 해당 하드웨어에 맞는 AIC8800DC 파일을
사용했습니다. v115를 Wi-Fi·오디오·RetroArch가 정상인 보존 기준본으로 삼았습니다.

## 2. 설치 전 Mali ABI 진단

가져온 TSPS Mali 모듈은 Action Pi 커널과 다른 위치에서 inode의 세 필드를 읽었습니다.
대상에서 관찰한 위치는 `i_rdev=0x34`, `i_mapping=0x20`, `i_private=0x238`이었지만,
가져온 모듈은 각각 `0x44`, `0x30`, `0x248`을 사용했습니다. `page`, `mm_struct`,
`dma_buf` 접근도 별도로 검토했습니다.

세 명령만 고치고 호환된다고 판단하는 대신, 고정한 공개 후보 커널 설정을 사용해
드라이버를 재빌드했습니다. Orange Pi 후보 커밋은
`5b956b750422abd5e9e9c5523540d2aaf41a7939`이며, Mali 소스는 Radxa 커밋
`2045a3ca2a01f088c0314dc924bda59d154e363e`의 r42p0-01eac0,
JM/sunxi/devfreq 구성입니다. Arm GNU 13.3.Rel1의 AArch64 Linux용 GCC 13.3.1을
사용했습니다.

컴파일 결과 올바른 inode 접근이 생성되었습니다. 외부 참조 심볼 301개 전체의 이름을
실제 기기 커널의 공개 심볼과 비교했습니다. 이는 이름이 제공됨을 확인한 것이며,
동작 의미까지 포함한 완전한 ABI 호환성 증명은 아닙니다. 후보 커널에서는 제조사 설정
심볼 세 개(`AW_GPU_TYPE`, `ENC_SW2001`, `JOYSTICK_RGP`)가 여전히 빠져 있었으므로,
정확한 원본 제조사 소스라고 설명하지 않았습니다. 최초 컴파일에는 `Module.symvers`도
없었습니다. `.ko`가 만들어졌다는 사실만으로 의존성 검증을 마친 것으로 보지 않았습니다.

## 3. 게임 실행마다 GPU 드라이버를 바꾸는 방식 회피

실행 중인 그래픽 세션에서 Panfrost를 제거하고 Mali를 올리면 GPU 전원 관리 상태가
남는 문제가 있었습니다. 처음부터 Mali가 GPU를 맡게 하자 초기 Vulkan 확인은 가능했지만,
DRM 종료·복원 과정에서 여전히 멈출 수 있었습니다. Vulkan 인스턴스 생성만으로 PPSSPP의
화면 출력이나 정상 종료를 입증할 수는 없었습니다.

최종 방식은 부팅부터 Mali를 유지하고 같은 그래픽 구성에서 호환되는 ES 메뉴를
실행하는 것입니다. 게임마다 Panfrost↔Mali를 바꿀 필요를 없앴습니다. 메뉴 시작 실패에
대비한 복구 경로는 남겼으며, 정상 경로는 Mali를 유지합니다.

## 4. 화면 클라이언트 수명 관리 수정

멈춘 DRM 복원 경로를 따라 출력 감지 작업자와 클라이언트 목록을 진단했습니다.
제한된 메모리 읽기로 읽기 실패, 구조체 배치 오해와 잘못된 목록 항목을 구분했습니다.
오프라인 코드 분석에서 유효하지 않은 잔여 항목이 초기 프레임버퍼 준비 실패 및
불완전한 정리와 연결됨을 확인했습니다.

소스 수정은 부팅 로고 연결 오류를 등록 전에 상위로 전달하고, 크기가 0인 경우를
거부하며, 메모리를 해제하기 전에 등록한 클라이언트를 정리합니다. 공개 후보에는 실제로
동작하는 플랫폼 정리 구현이 있었지만 실기 바이너리의 보조 함수는 비어 있었습니다.
따라서 알 수 없는 제조사 소스에 공통 코드 차이만 적용해서는 그 보조 함수가 복구되지
않습니다.

정확한 제조사 소스가 없어 v116에서는 기존 함수 세 개의 본문 안에 크기를 제한한 ARM64
수정과 검증한 분기 연결을 적용했습니다. 원본 바이트와 커널 해시를 확인했으며,
추측한 빈 공간으로 커널을 확장하지 않았습니다. 링크 공간, 재배치와 ARM64 모의 실행
사례 8개를 확인했습니다. 전체 이미지 비교에서는 허용한 커널·체크섬 범위 안에서
298바이트가 변경되었습니다. 이 모의 검증을 실기 검증의 대체물로 취급하지 않았습니다.

## 5. 렌더링 성공과 실제 패널 출력을 구분

Vulkan이 초기화되고 PPSSPP가 실행되는데도 실제 화면은 검정이었습니다.
최종 프레임버퍼를 읽자 알아볼 수 있는 게임 RGB 영상이 있었습니다. 프로세스 실행과
present 호출 성공만으로 눈에 보이는 출력을 확인할 수 없다는 뜻입니다. 이후 캡처에서
ARGB 버퍼 전체의 알파가 0인 것을 확인했습니다.

활성 출력 평면은 premultiplied blending을 사용하고 있었습니다. 애플리케이션의 기존
DRM master를 통해 픽셀 블렌딩 모드만 **None**으로 바꾸자 게임 화면이 즉시 보였습니다.
그 시험에는 DMA 일관성이나 출력 경로 변경이 필요하지 않았습니다. 이 결과는 직접적인
알파·블렌딩 불일치를 찾은 것이며, 알파 생성의 가능한 모든 원인을 밝힌 것은 아닙니다.
지속 적용용 불투명도 보조 기능은 PPSSPP 세션에만 보정을 적용하고, 정리 전에 복제한
master 파일 디스크립터를 닫습니다.

## 6. 프로그램 전체 회전과 입력 보정

패널의 원래 모드는 세로 720×960입니다. PSP 게임 영상만 회전하면 PPSSPP 인터페이스는
옆으로 남았습니다. 논리 해상도를 맞추지 않고 방향만 고치면 메뉴가 잘리고 게임이 작게
나왔습니다. 최종 래퍼는 애플리케이션 크기를 가로 960×720으로 맞추고 전체 출력을
회전합니다. 사용자가 게임·메뉴·크기·오디오·조작을 확인했으며 D패드 수정도 포함합니다.

ES 메뉴는 기존 화면 회전 옵션을 사용합니다. RetroArch의 SDL 렌더러에는 대상 텍스처
회전 보정을, GLES Flycast 경로에는 전체 출력 보정을 적용했습니다. 각 경로에만
적용하며 시스템 전체 SDL을 교체하지 않습니다.

## 7. 재부팅 없는 ES와 PPSSPP 연결

로더 환경을 올바르게 유지하면 ES도 제조사 EGL/GLES/GBM 구성으로 초기화할 수 있습니다.
ES 프로세스 그룹 밖의 관리 프로그램이 메뉴 정상 종료, DRM master 해제, PPSSPP
실행·종료와 메뉴 재실행을 조정합니다. 왕복 전후 부팅 ID가 같다는 것을 확인해
숨은 재부팅과 구분했습니다. 사용자도 평소 방식으로 게임을 선택하고 종료·메뉴 복귀를
확인했습니다.

자동 시작에는 다음 부팅의 복구 기능을 포함했습니다. 이후 실행 분배기가 과거
`knulli.conf` 사본을 현재 사용자 설정 위에 복원하지 않도록 고쳤습니다.
언어·시간대가 되돌아가는 문제를 해결하고 PPSSPP 설정도 유지하도록 했습니다.

## 8. 다른 에뮬레이터와 전원 수정

일반 Flycast와 스탠드얼론의 드림캐스트 회전을 보정했습니다. VL/Xtreme은 처음에는
드림캐스트 로고를 통과했지만 게임 진입 시 실패했습니다. 로고만 확인한 초기 보고를
최종 검증으로 보지 않았습니다. SDL의 evdev 비상 시그널 처리기를 거치며 원래 JIT
예외 문맥이 사라지는 문제였습니다. 최종 수정은 해당 구형 코어 두 개에만
`SDL_NO_SIGNAL_HANDLERS=1`을 설정합니다. 실험용 시그널 연결 방식은 폐기했습니다.
이후 두 코어 모두 게임에 진입했으며 사용자가 확인했습니다.

절전 직후 깨어나는 현상은 활성 AIC8800 SDIO가 절전 방지 잠금을 잡아서 생겼습니다.
Action Pi 훅은 Wi-Fi가 켜져 있었는지 기억하고 절전 전에 끈 뒤, 무선 장치가 준비되면
이전 ConnMan 서비스를 복구합니다. 토큰 확인으로 오래된 재연결 시도를 취소합니다.
사용자가 절전 복귀와 자동 재연결을 확인했습니다.

RetroArch의 HOME 종료는 작동합니다. PPSSPP의 HOME 종료는 정지와 복구 재부팅을
일으켜 비활성화했으며, SELECT+START를 약 1초 누르는 종료 방식을 유지했습니다.
초기 밝기 입출력 관찰 훅이 배경음악 끊김을 일으켰습니다. 읽기 경로 가로채기를 제거했고,
최종 길게 누르기 보조 기능은 실제 밝기 쓰기에만 적용하여 음악 파일을 읽을 때마다
검사하지 않습니다.

## 9. 실제 하드웨어 계층에서 밝기 재발 해결

v117/v118의 시도는 철회했습니다. 실제 PWM 신호가 맞으면 기기 본래의 증가 방향
밝기 값이 올바르게 동작합니다. 숫자 반전은 근본 문제를 일시적으로 숨겼을 뿐입니다.

첫째, 커널 뒤에 붙은 데이터의 DTB를 수정해도 실제 부팅에 사용되지 않았습니다.
실행 중인 장치 트리는 SD 오프셋 `0x1004000`에 있는 원시 TOC1 패키지의 외부 DTB에서
왔습니다. FAT의 사본도 실제 활성 패키지보다 오래된 것이었습니다. 실제
`/backlight0/pwms` 극성 플래그를 바꾸고 TOC 체크섬을 갱신한 뒤 FAT 패키지도
동기화했습니다. 부트로더 실행 코드는 변경하지 않았습니다.

둘째, 실행 중인 장치 트리의 극성이 정상이더라도 BSP 드라이버의 캐시 상태와 달리
실제 PCR 비트 8은 0으로 남았습니다. 완전히 껐다 켠 뒤와 절전 복귀 뒤 모두 이
불일치가 있었습니다. 보호 조건을 둔 정상화 기능이 보드, PWM 컨트롤러와 실행 인자를
확인한 뒤 부팅 후반과 복귀 훅에서 해당 물리 극성 비트만 설정합니다. 본래의 밝기 값과
길게 눌러 연속 조절하는 기능은 유지했습니다. 사용자가 완전 종료·시작과 절전·복귀를
확인했으며 레지스터 읽기에서도 두 경우 모두 0에서 256으로 바뀜을 확인했습니다.
이 구성이 안정판 v119가 되었습니다.

## 10. 공개 배포판 제작과 PortMaster

공개판은 영어 기본·Wi-Fi 꺼짐으로 구성하고, 현재 기본 설정과 복구 사본 양쪽에서
개인 네트워크 정보를 제거했습니다. 추가 BIOS 압축 파일은 제외하고 기본 시스템 BIOS는
유지했습니다. 디렉터리 항목만 지우지 않고 삭제된 FAT 클러스터와 파일 여유 공간을
0으로 채웠습니다. 기기 식별자, 쿠키, 사용 기록, 페어링과 진단 캡처는 설정 설치 자료에서
제외했습니다.

PortMaster 설치 뒤 Python/PySDL2 인터페이스가 왼쪽으로 회전되어 나왔습니다.
PySDL2는 이름이 지정된 DLL에서 함수를 찾으므로 이전 LD_PRELOAD 접근을 우회했습니다.
전용 SDL 보정 라이브러리가 작동하던 렌더러 보정을 재사용하고 나머지 심볼을 원래 SDL로
전달하도록 했습니다. PortMaster만 이 라이브러리를 선택합니다. 설치·업데이트가 실행
스크립트를 교체하면 실행 준비 단계에서 설정을 다시 적용합니다. 사용자가 방향과 크기를
확인했으며 공개 IMG에 포함했습니다.

## 11. PPSSPP 단독 실행 항목 통합

ES의 Emulators/PPSSPP 스크립트는 `PPSSPP`를 직접 호출하기만 했습니다.
정상 PSP 실행 경로와 같은 스탠드얼론 바이너리를 쓰지만, Vulkan ICD·출력 보정·
불투명도·세션 처리를 거치지 않았습니다. 별도의 libretro 코어는 존재하지만,
이 증상만으로 스탠드얼론 빌드가 두 개라고 볼 수는 없었습니다.

실행 분배기가 해당 Emulators 항목을 인식해 기존 관리 프로그램에 PPSSPP UI 실행을
요청하도록 바꿨습니다. ROM을 고르거나 보유할 필요가 없습니다. 세션 실행기는 UI 모드에서
게임 인자만 생략합니다. 일반 PSP 경로·확장자 검증, Vulkan 환경, 회전, 불투명도,
설정 유지와 SELECT+START 처리는 공유합니다. 설치 과정에서 한 차례 재시작하여 상주
관리 프로그램을 다시 불러왔습니다. 사용자가 Vulkan, 방향·크기와 메뉴 복귀를 확인했습니다.
이 수정은 공개판 v1.0.0(내부 빌드 v119 r2)과 개인용 v120 r2에 포함됩니다.
공개 버전 번호는 v1.0.0부터 시작하며, 이름 변경으로 이미지 내용은 바뀌지 않습니다.
